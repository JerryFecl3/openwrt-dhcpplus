# DHCP+ 协议与实现笔记

本文提炼已完成的研究结论，服务于实现维护与复现。适用范围是本项目已验证的辽宁联通 IPTV DHCP+ 分支，不将“DHCP+”“IPoE”视为全国统一的认证算法。对应源码基线：核心 0.3.0-r2、LuCI 0.3.0-r3。

本文不包含真实账号、设备身份、租约地址、现场 XID、认证报文或原始抓包。示例由人为选定的数值生成。

## 1. 核心结论

网络接入仍执行 DHCP Discover → Offer → Request → ACK。区别在于客户端 Option 60 携带与本次 DHCP 事务 ID（XID）相关的数据：

```text
Option60 payload = 00 00 1f 28 || SHA1(ASCII(decimal(XID) + "LUIOITDCNNCMPVHP"))
```

- 总长 **24 字节**：固定前缀 4 字节，加 SHA-1 摘要 20 字节。
- 输入使用 XID 的**无符号十进制字符串**，不是十六进制字符串或四字节原始数据。
- 十进制数和固定字符串之间没有分隔符；不包含换行或末尾 NUL。
- 摘要以原始二进制字节发送，不是 40 字符的十六进制文本。
- 本分支的计算不使用账号、密码、MAC、主机名或设备专属密钥。固定字符串是协议常量，不是用户密码。

Option 60 是 DHCP 的 Vendor Class Identifier 字段；这里描述的是特定实现赋予其载荷的含义，并非所有 Option 60 都采用该算法。

**计算未使用 MAC，不代表接入服务器不检查 MAC。** DHCP 报文还有以太网源地址、chaddr、Option 12/61 等字段，上游设备与服务器可另外实施策略。取得租约也不代表完成 IPTV 应用平台认证。

## 2. 字节级示例与最小复现

合成 XID：`0x12345678`，十进制为 `305419896`。

```text
摘要输入（ASCII）：305419896LUIOITDCNNCMPVHP
SHA1：91ef9616d635d9df44f6cd3d66b5b9278b6d0c8c
Option60 payload：00001f2891ef9616d635d9df44f6cd3d66b5b9278b6d0c8c
完整选项 TLV：3c 18 00 00 1f 28 91 ef 96 16 d6 35 d9 df 44 f6 cd 3d 66 b5 b9 27 8b 6d 0c 8c
```

`3c` 是选项编号 60，`18` 是十六进制长度 24；这两个字节不参与摘要，也不属于上述 payload。

可直接使用 Python 标准库复现，不访问网络：

```python
import hashlib

def option60(xid: int) -> bytes:
    if not 0 <= xid <= 0xffffffff:
        raise ValueError("XID must fit in uint32")
    message = (str(xid) + "LUIOITDCNNCMPVHP").encode("ascii")
    return bytes.fromhex("00001f28") + hashlib.sha1(message).digest()

assert option60(0x12345678).hex() == (
    "00001f2891ef9616d635d9df44f6cd3d66b5b9278b6d0c8c"
)
assert len(option60(0x12345678)) == 24
```

数学上可以对完整 uint32 范围计算摘要；本插件生成 **1 至 0x7fffffff** 范围的 XID。原设备使用 `lrand48()` 产生非负 31 位数，为采用这一范围提供了依据。非零是插件的选择，不能据此断言服务端拒绝零；也不能凭少量高位为 1 的失败样本断言服务端的全部判定规则。

## 3. 为什么普通 Option60 重放会失败

如果把固定 Option60 配给普通 udhcpc，而 udhcpc 自己生成另一个 XID，就可能失去二者的对应关系。旧值是否被服务器接受取决于其校验策略，不能把某条线路能重放视为通用保证。

本项目早期方案同时固定 XID 和捕获的 Option60；当前方案在每次接口客户端启动时生成**新的配对**，不依赖历史报文。OpenWrt 用 `-x 0x3c:<十六进制载荷>` 交给 udhcpc 进行二进制选项编码，不能直接当普通 vendor 字符串传入。

这里还存在字节序区别：

1. 算法中的 XID 是按报文网络序解释得到的整数。
2. 被验证的 udhcpc 将 `random_xid()` 的结果用于报文 XID 存储；辅助库用 `htonl()` 将选定整数转换为相应内存字节布局。
3. 不能看到 `htonl()` 就再对摘要输入做一次反转；摘要始终使用第 1 步的整数。

该机制依赖实际 BusyBox 的调用方式；更换版本或 libc 后，应检查 XID 生成与存储代码，而不是只验证脚本能运行。

## 4. 如何保持原版 udhcpc

实现只有三个安装文件：

| 文件 | 作用 |
| --- | --- |
| `/lib/netifd/proto/dhcpplus.sh` | 注册协议、生成配对、设置选项，复用原版 DHCP setup/renew/teardown |
| `/usr/lib/iptv/udhcpc-xid.so` | 对选定客户端进程中的 `rand()` 做符号替换 |
| `/www/luci-static/resources/protocol/dhcpplus.js` | 提供 LuCI 协议选项与默认值 |

启动过程：

```text
指定接口使用 proto=dhcpplus
  → 从 /dev/urandom 生成非零 31 位 XID
  → openssl 计算匹配的 Option60
  → 为本次客户端导出 IPTV_FIXED_XID 和 LD_PRELOAD
  → 调用系统 DHCP setup，启动原版 udhcpc
  → 动态加载器载入辅助库，rand() 返回预定的报文字节值
```

控制范围来自**启动时的进程环境**，不是扫描 PID 后修改已有进程，也不是使用主机名识别目标。只有经过 DHCP+ 启动路径的客户端获得这些环境变量；未修改 `/etc/ld.so.preload`、BusyBox 或全局 DHCP 脚本。

辅助库构造函数读取并保存 XID 后，清除 `LD_PRELOAD` 与 `IPTV_FIXED_XID` 环境变量。这不会卸载当前进程已加载的库，但可避免随后 exec 的 DHCP 事件脚本及其子程序继续继承该设置。

准确地说，钩子影响的是目标进程内所有经动态符号解析到它的 `rand()` 调用，并非仅某一条源码语句。因此依赖于已验证的 udhcpc 实现。静态链接的 BusyBox 或不同随机数实现不能直接假定兼容。

随机读取、摘要生成或必要辅助库检查失败时，协议启动返回 `DHCPPLUS_GENERATION_FAILED`，不会回退到旧摘要。

## 5. 随机数与续租的真实边界

| 行为 | 原设备研究结果 | 当前插件 |
| --- | --- | --- |
| 开始客户端/首次接入 | 生成 XID 并计算摘要 | 每次 setup 生成新配对 |
| 同一进程中的重传及续租 | 研究发现原设备开始续租事务会重新生成 XID/摘要 | 保持本进程启动时生成的同一配对 |
| 客户端重新启动 | 新事务 | 重新生成配对 |

所以“恢复随机”指**每次客户端启动随机**，不是每个包都随机，也不是已经逐次复刻原设备的续租 XID 更新方式。该折中使插件可以保留系统组件，而无需在 udhcpc 内部同步修改 Option60。

现有配对方式已取得完整 DORA 和显式续租 ACK；这证明该方式在测试线路可用，不能替代跨真实长租期自动续租、多日稳定性或其他线路验证。

## 6. 其他 DHCP 字段与配置

- **Option12 = hostname**。测试线路中，原设备主机名、任意普通主机名和不发送主机名均完成接入与显式续租。插件不要求固定长度；其他线路不保证相同。
- 当前协议默认 `hostname='*'`，不发送 Option12；显式设置普通主机名时由原版 udhcpc 处理。
- 默认不发送 Option61；默认请求选项列表为 `1 3 6 12 15 28 31 33`，关闭默认请求集合、Option121 和 6rd 请求。显式接口设置优先。
- 旧配置中的原始 Option12、Option60 别名和 vendorid 在本次运行时过滤，避免重复发送；不会自动删除用户 UCI 配置。旧 fixedxid 不再决定新配对。
- LuCI 新接口默认不采用 IPTV 网关作为主默认网关；这只是默认配置，已有显式设置仍有效。
- DHCP 返回了 DNS/网关但接口未采用时，数据可能仍在 netifd 的 inactive 字段中。是否纳入系统 DNS/主路由与是否成功获得这些字段是两件事。

## 7. 证据如何建立

此处只保留证据方法和结论，不发布原始材料：

1. **静态还原**：分析自有中兴 B860AV1.1 设备 DHCP 客户端的选项构造路径，确认固定前缀、十进制格式化、常量拼接、SHA-1 与 24 字节长度；另确认 31 位随机数来源与续租分支。
2. **离线比对**：两次开机过程中，四个不同 XID 对应的六条客户端 DHCP 消息，计算出的载荷与捕获值逐字节一致。
3. **在线接入**：独立生成的新配对获得 Offer；使用原生客户端配合插件完成 Discover、Offer、Request、ACK，以及显式续租 Request、ACK。
4. **自动生成集成**：自动生成版本的两轮客户端重建产生不同配对，每轮接入和显式续租均成功；客户端消息中的摘要计算正确。
5. **隔离检查**：现场检查默认路由、其他 DHCP 进程及系统 BusyBox/原 DHCP 脚本保持原状。

另有一次针对旧租约独立构造的 raw 续租得到 NAK，原因未确定。不把这一负例隐去，也不据此推导“算法错误”或“服务器绝不允许新 XID 续租”。成功的插件路径与该独立注入实验应分开评价。

二进制中还发现其他认证分支，涉及不同字段或密码处理；本项目没有据此实现或宣称兼容这些分支。区域名称相同也不能代替报文格式确认。

## 8. 排查与复现顺序

1. 确认 VLAN、交换路径和设备绑定，使请求确实到达运营商侧；客户端发出了 Discover 不代表服务端收到。
2. 在自己的线路上核对实际 XID，以及载荷长度、前缀、十进制输入和摘要。不要只看配置文本。
3. 区分无响应、Offer、NAK 和 ACK；只获得 Offer 尚未完成接入。
4. 比较 MAC/chaddr、Option12/61、广播标志等其他条件，避免把所有失败归于摘要。
5. 分别验证首次接入、显式续租、接口重新启用及真实租期下的自动续租。

本项目提供的离线公式只生成字节，不发包、不接触路由器。真实接入测试需在自己的订阅线路和维护窗口进行。

## 9. 发布与维护边界

文档仅含协议常量、合成测试向量及汇总结论，不附原始抓包、固件/厂商库、完整反汇编、真实设备 MAC/序列号、业务凭据、地址租约或现场认证载荷。原材料留在本地研究档案。
